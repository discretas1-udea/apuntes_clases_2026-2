# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is not a software project — it's the class-notes log ("bitácora") for the course **Matemáticas Discretas 1**, Universidad de Antioquia (Ude@), semester 2026-2. There is no code to build, lint, or test. The only artifact type produced here is Markdown (`README.md`) plus the original class materials (PDF slides/handwritten notes, PPTX, Xournal++ `.xopp` files, and images) checked in as sibling files.

Each `clase-0N/` directory holds one class session's materials and, once finalized, a `README.md` summarizing it. `clase-01` through `clase-09` have their `README.md` written and finalized.

The root `README.md` is the course syllabus/schedule (cronograma) — a table of all sessions with links into each `clase-0N/` directory. When a new `clase-0N/README.md` is finalized, the corresponding row in the root table should be updated (notes link, content summary, observations). **As of v1.6**: add one row per session to the *visible* table, taking week/class number/date/title from the planned rows in the commented-out block (`<!-- ... -->`, which is the original plan and is never edited), filling the other columns in the format of the existing visible rows, with "Contenido" reflecting what was actually taught (a postponed topic doesn't appear), and linking only the current class's manuscript.

Tigarto (the user) is the course's professor; the annotated manuscripts are his own. README prose still calls him "el profesor".

## Generating a class README

The authoritative spec for writing `clase-0N/README.md` is **`prompt_maestro_apuntes_clase_v1.6.md`** (root of repo) — always read the latest-numbered `prompt_maestro_apuntes_clase_v*.md` file, since it supersedes older versions kept for history. Key points to internalize before writing or editing a class README:

- **Inputs**: handwritten notes PDF (primary source of truth), Zoom-derived material (secondary — good for student Q&A tone and per-responsible pending items, not for hard facts), and any other loose materials. A class taught across multiple calendar days can have Zoom material per session; when several exist, cross-reference them against each other and against the manuscript to resolve doubts about an exercise's real statement (e.g. a later session explicitly clarifying a transcription error from an earlier one). **As of v1.5**: a single session can also have more than one Zoom-derived artifact at different levels of detail (a narrative summary plus more granular notes/"contenido general" with verbatim quotes) — treat both together as secondary source, cross-checked against each other. Wait for explicit instruction before generating — don't generate speculatively. **As of v1.6**: start with a checklist of available/missing inputs; Tigarto then usually hands over Zoom material one piece at a time — acknowledge each (which session, which type), note what's relevant, and ask for the next until he explicitly says there's no more. A Zoom artifact's date can be off by a day (time zone); identify the session by content.
- **Fixed structure/order**: `Built with AI` badge → `# Clase N — Title` → metadata blockquote (date(s), modality, links to materials) → Objetivos de la clase → Resumen → Agenda → Contenido temático (conditional) → Datos del docente (conditional) → Medios de comunicación (conditional) → Recursos del curso (conditional) → Evaluación (conditional) → Pendientes (Docente/Estudiantes subsections, omit empty ones) → Próxima clase (omit if unknown, never write a "Por definir" placeholder).
- **Conditional sections only appear when that class actually touched/changed that topic** — do not repeat them every class out of habit.
- **Objetivos** are 2-4 bullets phrased as the instructor's session goals ("Presentar...", "Establecer...", "Definir..."), never as student-facing skills or bare topic names.
- **Agenda** reflects the order things were actually taught (per the handwritten notes), not an idealized slide order. If a class spanned multiple calendar days, split the Agenda by session with `**Sesión N — fecha**` subheadings. **As of v1.4**: locate the real session boundary by looking for an explicit date marker inside the manuscript itself (often handwritten between two slides, e.g. "Fin: DD/MM → Inicio: DD/MM"), cross-checked against each session's Zoom summary when the manuscript doesn't mark every boundary — don't assume the split lines up with a topic's "natural" end or with the order of an intro agenda slide (a real chronology error was caught and fixed this way while drafting `clase-07`). **As of v1.5**: the same date-marker trick can reveal that the manuscript/PPTX bundles slides prepared for a *future* class beyond the current one's own sessions (a start date that doesn't match any date of the class being documented) — exclude that content from "Contenido temático" (not yet taught) and only mention it in "Próxima clase" if useful, never as already covered (caught while drafting `clase-08`, where the manuscript ran ahead into the next class's material). **As of v1.6**, the inverse case: a session of the current class may start on the last pages of the *previous* class's manuscript (e.g. leftover exercises; `clase-09`'s 22/09 session began on `clase-08` pp. 48–58) — that content *is* included in the current class, the previous manuscript is linked in the metadata with its page range, its exercises are labeled `Ejemplo N (clase 8)`, and the previous (finalized) README is left untouched. Also as of v1.5: Agenda items that reference another section (`(→ sección N)`, `(→ Evaluación)`) are written as Markdown anchor links to that heading, not plain italic text, to ease review of long documents — not required retroactively on already-finalized classes.
- **Contenido temático** is an expanded theory recap organized in numbered `### N. Tema` subsections — explanations, tables/diagrams, formulas, and code actually used in class (never invented examples). Images referenced go in the same `clase-0N/` directory via relative path (`./nombre.png`); **as of v1.4**, a diagram may instead be a ```` ```mermaid ```` code block (rendered natively by GitHub, no binary file needed) — prefer Mermaid when the diagram visualizes a conceptual relationship between terms already defined in the text, and reserve manuscript screenshots for visual content a table/prose genuinely can't reproduce (not just to "decorate" a section already well covered in text). Link to the corresponding section of the course's theory site (`discretas1-udea.github.io/discretas1-udea-20262/...`) as a "profundizar" reference — if the theory site lags behind the current class, link the most recent page actually published instead of an unconfirmed URL for the current class. **As of v1.3**, proofs worked in class in claim-reason (afirmación-razón) format may be reproduced in full as a table (`#`, `Afirmación`, `Razón`) when it adds clarity, transcribed faithfully from the annotated manuscript or from a separately-sent correction file — this includes pedagogically relevant failed/partial attempts, as long as their outcome is documented. **As of v1.6**:
  - Contenido temático also follows the real teaching order — never reorder it "theory first, exercises after"; use a cross-reference line instead.
  - It must be self-contained: open with a "Cómo leer este apunte" note plus a notation table (e.g. `≡` vs `→`), define terms before use, put long reference tables the class relied on in a `<details>` block, and close with an unnumbered `### Síntesis de la clase` (4–5 key ideas, nothing new) plus an "Errores y dudas de esta clase" box listing only what actually happened or was asked.
  - Mermaid diagrams are either a *figura de clase* (reproduces something shown/drawn, cite the page) or an explicitly labeled *Esquema del apunte* (own synthesis of steps actually used); never pass off a synthesis as class material.
  - When example numberings collide, disambiguate by class (`Ejemplo 4 (clase 8)`) or by content (`Ejemplo de Bart y Milhouse`).
- **Source-of-truth rule**: the handwritten PDF wins over the Zoom summary on any hard fact (dates, numbers, names). Report — don't silently resolve — any student-relevant discrepancy between sources. Never invent or complete missing data (e.g. a "por definir" exam date stays undefined). **As of v1.3**: if the manuscript itself has a minor internal inconsistency (e.g. a proof step citing the wrong prior step number), transcribe it as-is and flag it with a brief clarifying note rather than silently correcting it — the manuscript is the source of truth, even against itself. **As of v1.4**: when Tigarto relays a "correction" audit from another AI tool (Gemini, ChatGPT, etc.) on an already-drafted class README, verify each proposed change against the manuscript individually before applying it — the recurring failure mode is such tools grading the README as if it were a formal-logic/math textbook chapter and proposing to replace content transcribed faithfully from the professor (his terminology, examples, simplifications) with a more rigorous version he never actually taught. Reject those, citing the manuscript page or Zoom line where the original wording is; only apply corrections that fix a genuine drafting error or an internal inconsistency within the README itself. **As of v1.5**: there's a third path beyond accept/reject — when the audit's concern is valid (e.g. a real internal inconsistency with another concept from the same class) but the flagged content is a faithful quote of the professor's own material, keep the quote verbatim and add a short clarifying note (`[!NOTE]`/`[!TIP]`) next to it instead of rewriting the source or rejecting the concern outright; base that note on an actual in-class clarification from the Zoom material when one exists (e.g. a professor's answer to a student's question), not on a generic reformulation from the auditing tool (used twice while drafting `clase-08`). **As of v1.6**:
  - **Professor's conceptual errors** (distinct from a minor internal inconsistency): when Tigarto confirms an in-class error (e.g. a translation that changes the statement's meaning), transcribe the manuscript version as-is, follow it with a `[!WARNING]` starting "**Error del profesor en clase.**" that explains why it's wrong *in terms of meaning* and shows the corrected version, then a `[!TIP]` moral, and list it in the synthesis box. Don't soften it. A Zoom summary showing the correct version does *not* prove the error didn't happen — students watch the video, and Zoom's AI may "fix" what it summarizes (see `clase-09`, Ejemplo 5 of the cachivaches).
  - **"Aclaración del apunte"**: anything added while drafting rather than said in class (deductions from exercise data, connecting observations, schemas, source citations such as Russell & Norvig) is labeled *Aclaración del apunte* (italic paragraph, or a callout when it deserves emphasis). "Un estudiante preguntó…" callouts are reserved for what really happened.
  - Only add such clarifications when conceptually important for *that* class. Don't open a topic the class didn't cover even if a diagram exposes it — a neutral one-liner is enough — and ask Tigarto before writing anything that decides between versions of the material.
- **Voice**: formal (*usted*) in any student-facing prose; refer to the instructor as "el profesor", never by name, in narrative sections. Likewise, anonymize any student names that appear in Zoom-derived Q&A as "un estudiante" / "los estudiantes".
- **File layout convention**: each class is `clase-0N/README.md` plus sibling material files (PDF slides, PPTX, annotated manuscript PDF/`.xopp`, images) in the same directory, referenced with simple relative paths — no absolute paths or external URLs for files that live in-repo. **As of v1.3**: a professor's post-class correction to a specific exercise is a separate sibling file named `correccion_ejemploN_annotated.pdf` (plus its `.xopp` source), linked both in the initial metadata block and at the point in "Contenido temático" where that exercise is discussed (see `clase-05/correccion_ejemplo4_annotated.pdf` for a concrete example).
- **Recurring course principles** (as of v1.6) are repeated on purpose with fixed wording wherever a real example from the class illustrates them, never as boilerplate — e.g. *"Las formas aristotélicas son una guía, no una receta exhaustiva para todo el lenguaje natural."*
- **GitHub rendering gotchas** (as of v1.6):
  - Alerts (`[!NOTE]`, etc.) don't render inside list items, and Mermaid blocks shouldn't go inside lists either — keep both at top level.
  - Leave a blank line after an alert, or the next line is absorbed into it.
  - Escape `|` inside code in a table cell as `\|`.
  - Reserve callouts for what deserves emphasis (errors, morals, class Q&A, warnings); put other clarifications in plain paragraphs to avoid callout overload.
- **Optional three-perspective review** (as of v1.6, Fase 4): on request, review the draft as a first-semester student, as the lead professor and as an academic math-textbook editor, scoring each 0–100 with prioritized fixes. Explicitly discard editor suggestions that break fidelity (reordering, formal rigor not taught, LaTeX).
- Once a class `README.md` is approved, treat it as finalized: don't retroactively edit it if a later class announces a change (e.g. schedule change) — document the change in the later class's own `README.md` instead.

Older spec versions (`prompt_maestro_apuntes_clase_v1.md`, `v1.1.md`, `v1.2.md`, `v1.3.md`, `v1.4.md`, `v1.5.md`) are kept in the repo root for history; do not follow them over v1.6.

## Naming conventions observed in the repo

Directory names inconsistently use `clase-0N` (dash) at the top level, but files inside sometimes use `clase0N`/`claseN` (no dash) — follow whatever naming the existing files in that specific directory already use rather than imposing a single convention across the repo.
